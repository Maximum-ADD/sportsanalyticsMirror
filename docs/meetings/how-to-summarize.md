# Meeting Minutes Generation — LLM Instructions

Paste this whole file into whichever LLM you're using (Claude, ChatGPT, Copilot, etc.), along
with the raw transcript, to produce a minutes page for the docs site. Log the conversation in
`docs/ai-usage.md` per usual — this counts as AI-assisted document generation.

## Your task

You will be given a raw meeting transcript (auto-generated by Craig, so it may contain
misattributed speakers, filler words, and transcription errors). Turn it into a structured
minutes page for a university software project's documentation site.

## Output format — follow this exactly

```markdown

??? YYYY-MM-DD — [Client meeting / Standup]

   **Attendees:** Name1, Name2, Name3
   **Absent:** Name4 (reason, if stated)

   ## Agenda

   - Topic actually discussed, in the order it came up
   - Topic actually discussed

   ## Decisions

   - Decision made, and the reasoning given for it
   - Decision made, and the reasoning given for it

   ## Actions

   | Action | Owner | Due |
   |---|---|---|
   | Concrete task | Name | Date if given, else "TBD" |

   ## Notes

   Anything else worth capturing — blockers, open questions, things flagged for next time.

   #### note "Raw transcript (Craig)"
   [YYYY-MM-DD-{client|standup}.txt](../../transcripts/YYYY-MM-DD-{client|standup}.txt)
```
NOTE:

The ??? note block must contain the entire minutes summary, including Attendees, Agenda, Decisions, Actions, and Notes.
Everything inside the ??? block must be indented by 4 spaces.
Use ???, not ???+, so the summary is collapsed by default.
Do not put the raw transcript inside another collapsible/admonition block.

## Rules

1. **Only include what was actually said.** Do not infer decisions that weren't explicitly
   made, invent action owners that weren't assigned, or smooth over disagreement into false
   consensus. If the transcript is ambiguous about who owns an action or when it's due, write
   `TBD` rather than guessing.
2. **Attribute correctly, or flag it.** Craig's speaker labels are sometimes wrong. If you're
   not confident who said something, write `[speaker unclear]` rather than assigning it to the
   wrong person — misattributing a decision or commitment to the wrong teammate is worse than
   leaving a gap.
3. **Cut filler, keep substance.** Skip small talk, "can everyone hear me," restated agreement,
   and repeated points. Do not skip disagreement, pushback, or a decision being reversed
   mid-meeting — those are exactly the things worth a line in the individual/group report later.
4. **Don't editorialize.** No commentary on how the meeting went, how productive it was, or
   whether decisions were good ones. State what happened, not an opinion of it.
5. **Keep it scannable.** A marker or teammate should get the gist in under a minute. If the
   agenda has more than ~8 items or actions has more than ~10 rows, you're probably including
   things that were mentioned but not actually discussed — trim to what mattered.
6. **Leave the transcript link as a placeholder path** — do not paste the transcript into the
   file. It's stored separately as a `.txt` file linked from the collapsed section. You (the
   LLM) don't need to see or reproduce it in full; you're producing the structured summary from
   it.
7. **Client meetings vs standups:** client meetings should capture anything resembling a
   requirement, scope decision, or feedback the client gave, even a small offhand comment — that
   evidences Stakeholder Interaction. Standups should capture blockers and cross-team
   dependencies more than routine "I did X yesterday" status, since that's what actually needs
   follow-up.

## If the transcript is unusable

If the transcript is too garbled, too short, or missing entirely for a stretch of it, say so
explicitly at the top of your output rather than fabricating plausible-sounding content to fill
the gap: `> Transcript incomplete/unclear from [timestamp] — summary based on partial audio.`
