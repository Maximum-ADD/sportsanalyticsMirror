GOAL
Reduce how often, and how expensively, the API queries the Supabase
Postgres database, and introduce caching where the data allows it.

WHAT THE INVESTIGATION FOUND
- Nothing was cached anywhere. Every page view, tab refocus and
  signed-in request went to Postgres.
- React Query's defaults (staleTime 0, refetch on window focus) re-ran
  all 41 queries on mount and on every tab switch.
- Every signed-in request re-read the Session and User tables through
  BetterAuth.
- Heavy public reads ran per request: /players/leaders and sorted
  player lists scanned the whole player table plus a groupBy over
  ~80k boxscore rows; both analytics routes scanned every completed
  game; elo-ratings and /games/seasons ran full scans.
- Redundant queries: /players/:id/stats ran the same query twice,
  /stats/splits ran four, /players/compare ran two per player, and
  /games/:id/prediction re-fetched a prediction it had already joined.
- The Game table had no index on gameDate, homeTeamId or awayTeamId.

WHAT WAS IMPLEMENTED
1. An in-memory response cache in apps/api/src/cache/. It de-duplicates
   concurrent identical loads, never stores errors or nulls, bounds
   itself to 500 entries, and disables itself under Vitest.
   TTLs: 5 minutes for derived data, 1 hour for teams/seasons,
   60 seconds for leaderboard counts. Only public, non-user-specific
   reads are cached; nothing under /v1/me is.
2. Query consolidation: /players/:id/stats 3 -> 2 queries,
   /stats/splits 5 -> 2, /players/compare (4 players) 8 -> 2,
   /games/:id/prediction 2 -> 1, leaderboard counts 3 -> 2. The
   now-unused PredictionsService was deleted.
3. Frontend: a 5-minute staleTime and no refetch on window focus.
4. BetterAuth session cookie cache (5 minutes), removing the per-request
   session lookup. Trade-off: a session revoked elsewhere can stay valid
   for up to 5 minutes; sign-out and account deletion are immediate.
5. New indexes on Game(gameDate), Game(homeTeamId, gameDate),
   Game(awayTeamId, gameDate), PlayerGameStat(gameId) and
   Player(teamId).
6. Beat the Model: the card kept showing the game just called while the
   next one loaded, replayed a called game after navigating back, and
   got stuck on a 409. It now drops the called game immediately, loads
   the next one behind the graded result, always revalidates on mount,
   and skips a game that was already called. The server now breaks
   same-date ties on id so the next game is stable.

# Cut database round trips: caching + query consolidation

## Context

The API (NestJS + Prisma, one Render free-tier instance) talks to Supabase Postgres through the transaction pooler. Code comments already note that each round trip costs real latency there, and big row pulls use up Supabase compute and egress. Nothing is cached anywhere today, so every page view, tab refocus and signed-in request goes to Postgres. The data is almost read-only: games, stats, predictions and lineups change only when the Python batch jobs (`apps/ingestion`, `apps/predictor`, `apps/optimizer`) run. That makes short-TTL caching safe.

**Where the calls come from:**

1. **Frontend refetches too often.** `apps/web/src/main.tsx` uses `new QueryClient()` with defaults: `staleTime: 0` and `refetchOnWindowFocus: true`. The 41 `useQuery` calls refetch on every mount and every tab switch. `PlayerCards.tsx` and `PredictionsPage.tsx` also fire one `GET /v1/games/:id` per upcoming game, and each of those costs 3 DB queries.
2. **Every signed-in request does a session lookup.** `SessionAuthGuard` calls `auth.api.getSession()`, which reads the Session and User tables. BetterAuth's `useSession` hits `/auth/get-session` again on every load and refocus.
3. **Heavy public reads run on every request:**
   - `/players/leaders` and ranked `/players?sort=` each scan the whole player table plus a groupBy over about 80k boxscore rows.
   - `/analytics/model-accuracy` and `/analytics/leaderboard` each scan every completed game.
   - `/teams/elo-ratings` runs two distinct-scans.
   - `/games/seasons` runs a distinct-scan.
4. **Some endpoints make redundant queries:**
   - `GET /players/:id/stats` runs the same stats query twice.
   - `/:id/stats/splits` runs 4 queries where 1 would do.
   - `/players/compare` runs 2 queries per player.
   - `/games/:id/prediction` re-fetches a prediction it already joined.
   - The leaderboard runs 2 groupBys where 1 would do.
5. **Game has almost no indexes.** Only `seasonType` is indexed. There is nothing on `gameDate`, `homeTeamId` or `awayTeamId`, yet most queries filter or sort on those.

**Goal:** far fewer and cheaper DB hits with no behaviour change. The worst case is data up to about 5 minutes stale after a batch job runs.

## Phase 1: In-memory response cache in the API (biggest win)

An in-process cache fits here: there is a single Render instance, and nothing needs to be shared across processes. Redis or Upstash would add a network hop and a cost for no gain. The cache empties when the free tier spins down, which is fine.

**New `apps/api/src/cache/response-cache.service.ts`** (no new dependencies):

- `getOrLoad<T>(key, ttlMs, load): Promise<T>`
  - Returns a live entry if one exists.
  - Otherwise it single-flights the load: concurrent callers for the same key share one in-flight promise. This matters because `PlayerCards` fires parallel identical requests.
  - Rejections are not cached. `null` results are not cached either, so a 404 never sticks.
- `invalidate(prefix)` drops every key that starts with the prefix.
- The map is capped at about 500 entries and evicts the oldest first, using `Map` insertion order. This keeps memory bounded on the 512 MB instance.
- It passes straight through (no caching) when `process.env.VITEST` is set or `API_CACHE_DISABLED=true`. The e2e specs truncate and reseed one shared DB, and CI writes its own `.env.test`, so auto-detecting Vitest avoids touching CI.

**Supporting files:**

- `apps/api/src/cache/response-cache.module.ts` is a `@Global()` module exporting the service. Import it in `app.module.ts`.
- `apps/api/src/cache/cache-ttl.ts` holds named TTLs:
  - `REFERENCE_DATA_TTL_MS` = 1h (teams, seasons)
  - `DERIVED_DATA_TTL_MS` = 5min (stats, games, predictions, Elo, lineups)
  - `USER_ACTIVITY_TTL_MS` = 60s (leaderboard user counts)

**Where it applies.** Wrap at the service layer, not in a controller interceptor, so shared sub-results are cached once and keys only include the params that matter:

| Service method | Key shape | TTL |
|---|---|---|
| `GamesService.getSeasons` | `games:seasons` | reference |
| `GamesService.getGames` | `games:list:{status}:{season}:{seasonType}:{page}:{pageSize}` | derived |
| `GameDetailService.getGameDetail` | `games:detail:{id}` | derived |
| `TeamsService.getTeams` / `getTeamById` | `teams:list:{search}:{page}:{pageSize}` / `teams:id:{id}` | reference |
| `TeamsService.getEloRatings` | `teams:elo` | derived |
| `TeamsService.getSuggestedPlayers` | `teams:suggested:{id}:{count}` | derived |
| `PlayersService.getPlayerById` | `players:id:{id}` | derived |
| `PlayersService.getPlayerSeasonStats` | `players:stats:{id}:{seasonType}` | derived |
| `StatsService.getSeasonLeaders` | `players:leaders:{seasonType}:{minGames}` | derived |
| `StatsService.getPlayersRanked`: cache the **players + totals intermediate** keyed by `teamId/position/search/seasonType/participated`, so changes to sort, order, page or minGames never touch the DB | `players:ranked-base:{...}` | derived |
| `StatsService.getMatchupProjection` | `players:matchup:{id}:{seasonType}` | derived |
| `EvaluatedGamesService.getEvaluatedGames` (shared by both analytics routes) | `analytics:evaluated-games` | derived |
| `LeaderboardService` user candidates | `analytics:leaderboard-users` | user activity |
| `OptimizerService.getLatestLineup` / `getLatestPlayerPredictions` / `getPlayerPrediction` | `optimizer:*` | derived |

- **Invalidation:** after a successful insert, `PicksService.createPick` calls `cache.invalidate("analytics:leaderboard")`. The user's own rank then updates immediately.
- **Deliberately not cached:** everything under `/v1/me` (watchlist, team results, picks, challenge, saved items, profile). These are per-user, change often and are already cheap.
- **Cached values are shared references,** so callers must treat them as read-only. Every current caller builds new objects rather than mutating, and the service carries a comment saying so.

## Phase 2: Consolidate redundant queries

1. **Player stats:** `PlayersController.getPlayerStats` fetches `getPlayerSeasonStats` once and derives both `deriveSeasonAverages` and `deriveGameLog` from those rows. Add a `StatsService.getPlayerSeasonLine(id, seasonType)` for this. Goes from 3 queries to 2.
2. **Season splits:** `StatsService.getPlayerSeasonSplits` calls the existing `PlayersService.getPlayerSeasonStatsBatch([playerId])` with no seasonType (one query across all segments), groups rows by `stat.game.seasonType`, and derives each segment. Segments with no rows still get zeroed lines. Goes from 4 queries to 1.
3. **Compare:** `PlayersController.comparePlayers` uses a new `PlayersService.getPlayersByIds(ids)` (one `findMany` with `id: { in }` and team included) plus the existing `StatsService.getPlayerStatsBatch(ids, seasonType)`. It still returns 404 naming the first missing id, and keeps the response order. Goes from 2N queries to 2.
4. **Game prediction:** `GamesController.getGamePrediction` returns `game.prediction`, which `getGameById` already includes. Remove `PredictionsService` and its spec, since they are now unused, and drop it from `games.module.ts`. Goes from 2 queries to 1.
5. **Leaderboard counts:** `LeaderboardService.readUserCandidates` uses a single `gamePick.groupBy({ by: ["userId", "outcome"] })` and folds the calls and correct counts in Node. Goes from 3 queries to 2.
6. **Matchup projection:** `StatsService.getMatchupProjection` runs the opponent-stats query and `getUpcomingGamesForTeam` in parallel with `Promise.all`. Same query count, but less time holding the pooler.

## Phase 3: Stop the frontend refetch storm

- In `apps/web/src/main.tsx`, set `new QueryClient({ defaultOptions: { queries: { staleTime: 5 * 60_000, refetchOnWindowFocus: false } } })`, with a comment tying the value to the API cache TTL.
  - Every mutation already calls `invalidateQueries` (FollowPlayerButton, BeatTheModelCard, WatchlistBoard, ProfilePage, OnboardingPage, OptimizerPage). Invalidation refetches active queries whatever the `staleTime`, so updates after a mutation still show up immediately.
  - The test helper `src/test/renderWithProviders.tsx` builds its own client, so tests are unaffected.

## Phase 4: Skip the per-request session lookup

- In `apps/api/src/auth/auth.config.ts`, add `session.cookieCache: { enabled: true, maxAge: 5 * 60 }` with an explanatory comment.
  - BetterAuth then verifies a signed session cookie instead of querying Session and User on every guarded request and every `/auth/get-session`.
  - **Trade-off:** a session revoked from another device, or a role change made directly in the DB, can take up to 5 minutes to take effect. Sign-out and delete-user clear the cookie immediately.
  - The e2e specs mock `auth.api.getSession`, so they are unaffected.

## Phase 5: Indexes for the queries that remain

- In `schema.prisma`, on `Game`, add:
  - `@@index([gameDate])`
  - `@@index([homeTeamId, gameDate])`
  - `@@index([awayTeamId, gameDate])`
- On `PlayerGameStat`, add `@@index([gameId])`. The existing `@@unique([playerId, gameId])` already covers lookups by playerId.
- On `Player`, add `@@index([teamId])`.
- Generate the migration with `npx prisma migrate dev --name add_query_indexes`. It is applied on Render automatically by the existing `prisma migrate deploy` start command.

## Tests and verification

- **New unit spec** `apps/api/src/cache/response-cache.service.spec.ts` covers:
  - hit and miss
  - TTL expiry (with `vi.useFakeTimers`)
  - single-flight: concurrent callers trigger one load
  - rejected loads and `null` results are not cached
  - prefix invalidation and max-entry eviction
  - pass-through when disabled

  This keeps the 80% coverage threshold.
- **Update existing unit specs** whose constructors gain a cache argument: `stats.service.spec.ts`, `teams.service.spec.ts`, `games.service.spec.ts`, `watchlist-averages.spec.ts`. Pass a disabled or pass-through cache. Add cases for the consolidated splits, compare and leaderboard paths.
- **API:** in `apps/api`, run `npm run lint`, `npm run build` and `npm test` (the e2e specs need the local test Postgres on port 55433 via docker-compose). The existing `players`, `games`, `analytics` and `picks` e2e specs cover the response shapes of the consolidated endpoints.
- **Web:** in `apps/web`, run `npm run lint`, `npm test` and `npm run build`.
- **End to end:** run the API with `PRISMA_LOG_QUERIES=true` and the web dev server, then click through the Phase 0 pages. Expect:
  - the second visit and tab refocus log zero queries for public data
  - sort, page and order changes on Players log zero queries after the first load
  - `/players/:id/stats/splits` logs 2 queries, not 5
  - signed-in page loads log no Session or User reads within the 5-minute window
  - making a pick still updates the leaderboard straight away
